## 一句话结论

内容站最上游的决定不是页面框架，而是内容模型。先把“一篇内容由哪些字段组成”固定下来，页面和接口才不用反复改。

## 它解决什么问题

如果先写页面，内容结构会被组件倒推：卡片需要标题和摘要，详情页需要标签，SEO 需要日期。字段散落在组件里，新增一种视图就要再加一次。

这个示例先把内容放进 `content/`，用 frontmatter 描述元信息：

```yaml
---
title: "演示标题"
summary: "一句话结论"
type: tool
date: 2026-11-02
tags: ["工具", "演示"]
---
```

目录分两层：`notes/` 放短笔记，`articles/<系列>/` 放长文。slug 由文件名或目录名决定，长文则在 frontmatter 里显式声明。

## 一次小实验

创建一篇笔记后，先不写页面，只运行校验：

```bash
cd frontend
npm run content:validate
```

输出会给出内容总数和草稿数。此时页面还不存在，但内容契约已经可以执行。下一步再让接口读取同一份目录。

## 坑和限制

slug 是 URL，不是普通文件名。改名会改地址，旧链接会断；写之前要想清楚。

目录结构一旦被内容管线依赖，就不能随意移动。例如 `00-目录.md` 被约定为系列索引并跳过，改名后它会被当成普通文章。

## 适合谁

适合准备长期写、希望内容可备份可迁移的人。先接受 Git 和文件系统，再享受没有数据库、没有后台的简单部署。
