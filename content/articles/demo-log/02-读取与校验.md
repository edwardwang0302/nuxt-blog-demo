## 一句话结论

内容读取应该只有一个入口。页面、接口、RSS 和 sitemap 都从同一条链路拿数据，草稿过滤和排序才不会在不同地方出现分歧。

## 它解决什么问题

最直接的写法是在每个页面里读文件。页面少时可行，但很快会出现三套逻辑：目录按日期倒序，RSS 按日期正序，系列页还要按系列分组。任何一处忘记过滤草稿，草稿就会从另一个出口泄露。

这个示例把扫描、解析、校验和聚合放在 `frontend/server/utils/content.ts`，对外暴露 `loadContent()`、`toNoteSummary()`、`aggregateTags()` 和 `aggregateSeries()`。

## 一次小实验

读取目录接口：

```bash
curl -s http://localhost:3000/api/notes
```

返回值同时包含：

- `notes`：已发布内容的摘要，按日期倒序；
- `tags`：标签及每个标签下的内容数量；
- `series`：系列及系列内按日期升序排列的内容。

再访问详情接口：

```bash
curl -s http://localhost:3000/api/notes/demo-image
```

详情会额外返回渲染后的 HTML。Markdown 渲染时关闭原始 HTML，避免把不可信标签直接输出到页面。

## 坑和限制

YAML 可能把未加引号的日期解析成 `Date`，非法日期会被悄悄滚到另一天。示例使用 `JSON_SCHEMA`，让日期保持字符串，再由 schema 判断是否合法。

标签是自由文本，`Nuxt` 和 `nuxt` 会分裂。内容量上来后需要白名单或统一大小写。

## 适合谁

适合希望先把内容层做稳、再扩展页面的项目。读取链路集中后，新增一个视图通常只需要组合已有函数。
