## 一句话结论

页面不应该知道文件在哪里。它请求接口、渲染数据、处理交互；内容读取、草稿过滤和图片路径都在服务端完成。

## 它解决什么问题

如果页面直接导入 Markdown 文件，服务端和客户端会各自打包一份内容，首屏体积随文章数量增长；图片路径也要在组件里重新计算。

这个示例的页面通过 `useFetch('/api/notes')` 获取摘要，通过详情接口获取正文 HTML。主题状态由 `useTheme` 管理，首屏前用内联脚本写入 `data-theme`，避免亮暗切换闪烁。

## 一次小实验

启动生产构建：

```bash
cd frontend
npm run build
```

`prebuild` 会先校验内容；校验通过后才生成 `.output/`。然后启动产物：

```bash
node .output/server/index.mjs
```

抽查三类出口：

```bash
curl -s http://localhost:3000/rss.xml
curl -s http://localhost:3000/sitemap.xml
curl -sI http://localhost:3000/notes/demo-image
```

RSS 和 sitemap 只包含已发布内容；详情页返回 200；草稿地址返回 404。

## 坑和限制

部署时必须把 `content/` 一起放进镜像或挂载卷，否则运行时读取不到内容。示例支持用 `NUXT_CONTENT_DIR` 覆盖默认路径。

图片资源路由只允许固定扩展名，也不做压缩和 CDN。图片多时，需要把资源处理移到构建阶段或对象存储。

## 适合谁

适合需要 SEO、又不想维护数据库的博客。页面职责单一，内容层集中，部署产物是一个可以直接用 Node 启动的目录。
