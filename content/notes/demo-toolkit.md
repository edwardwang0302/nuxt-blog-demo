## 结论

Markdown 只解决正文怎么写，frontmatter 才定义一篇内容需要哪些字段。把字段写成 schema，并在构建前运行校验，错误会在本地暴露，而不是等发布后才被发现。

## 它解决什么问题

当内容只有几篇时，字段写错也能靠肉眼发现。数量上来以后，问题会变成：日期格式不统一、标签重复、slug 冲突、草稿误发布。这些问题不适合靠发布前自查解决，适合交给一段固定脚本。

这个示例把内容放在 `content/`，页面构建时直接读取。写作仍然在编辑器里完成，但每次构建都会先检查 frontmatter。

## 一次小实验

先写一篇合法笔记，再运行：

```bash
cd frontend
npm run content:validate
```

输出类似：

```text
内容校验通过：8 篇内容，其中 1 篇草稿。
```

再故意把 `type` 改成不存在的值：

```yaml
type: blog
```

校验会给出文件路径和字段名：

```text
内容校验失败（1 项）：
- notes/demo-toolkit.md: type: 类型必须是 tool、repo、experiment 或 article
```

构建会在 `prebuild` 阶段调用同一个脚本，所以错误内容不会进入产物。

## 限制

schema 能保证字段齐全、日期合法，但保证不了内容质量。校验器不知道一篇笔记有没有真实实验，也不知道结论是否可靠。后者只能靠写作规范和人工检查。

另外，标签是自由文本。`Nuxt` 和 `nuxt` 会被当成两个标签；内容多起来以后，需要白名单或规范化策略。

## 适合谁

适合自己写内容、能接受 Git 工作流、希望内容可备份可迁移的人。若作者不是开发者，或者需要多人协作、可视化编辑和媒体库，CMS 会更省事。
