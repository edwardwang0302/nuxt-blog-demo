## 结论

草稿不是“隐藏文件”，而是内容管线里的一个状态。它保留在仓库里，继续被校验，但所有面向读者的出口都会过滤掉它。

## 它解决什么问题

写作经常是分几天完成的。如果未完成的内容直接进入目录，读者会看到半成品；如果把它移出 `content/`，又容易忘记后续发布，也无法提前发现格式问题。

`draft: true` 让内容留在原位，同时从公开视图里消失。发布时只需要改一个字段，不需要移动文件。

## 一次小实验

这篇笔记本身就是实验对象。访问详情页：

```bash
curl -sI http://localhost:3000/notes/demo-draft
```

应返回 404。再检查目录接口：

```bash
curl -s http://localhost:3000/api/notes
```

返回的 `notes` 里不会出现 `demo-draft`。同类过滤也作用于首页、标签聚合、系列页、RSS 和 sitemap。

但运行内容校验时，草稿仍会被读取：

```bash
npm run content:validate
```

如果草稿的 frontmatter 有错误，构建仍会失败。这是刻意的：等到发布时才发现字段问题，修复成本更高。

## 限制

草稿仍然存在于 Git 历史中。如果内容包含敏感信息，不要用 `draft` 当访问控制；应该把内容放在独立仓库或私有存储里。

草稿的图片资源路由同样会拒绝访问，因为资源路由只服务已发布内容。

## 适合谁

适合一个人维护内容、希望提前写多篇再陆续发布的站点。草稿状态简单，但边界清楚：它解决发布节奏，不解决权限和保密。
