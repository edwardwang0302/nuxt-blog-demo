## 结论

内容校验放在 `prebuild`，比放在发布流程里更可靠。构建失败的成本很低，坏内容上线的成本很高。

## 它解决什么问题

frontmatter 是手写的 YAML，容易出现日期格式、字段拼写和标签重复问题。如果只在页面上观察结果，很多错误不会立刻显形：草稿可能直接消失，标签可能悄悄分裂成两个。

这次实验准备了两份坏文件：一份日期写成 `2026-02-30`，一份把 `tags` 写成字符串而不是数组。

## 一次小实验

把坏文件放进 `content/notes/`，运行：

```bash
cd frontend
npm run content:validate
```

输出会一次列出所有问题：

```text
内容校验失败（2 项）：
- notes/bad-date.md: date: 日期不是有效日期
- notes/bad-tags.md: tags: 期望数组，收到字符串
```

修好一份再运行，剩余错误仍会出现。校验器不会在第一条错误处停下，这样一次修改可以解决一批问题。

直接运行 `npm run build` 也会先触发校验，失败时不会生成新的 `.output`。

## 限制

这个实验只覆盖字段层。它无法发现正文里的死链、图片缺失或事实错误。图片路径错误会在访问资源路由时暴露，死链则需要额外的链接检查。

校验器依赖固定的 schema；新增字段时必须同步改 schema、文档和测试，否则会被 `.strict()` 拒绝。

## 适合谁

适合已经在用 Markdown 写作、但还没有构建前检查的人。先把校验接上，再逐步增加链接检查和图片检查。
